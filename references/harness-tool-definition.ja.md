## 1. 何の道具か

**2 つの言い方があり、どちらも同じものを指す。**

| 見る向き | 言い方 |
|---|---|
| **下から** | **持っている hardware を CH32 の道具にする、標準の口。** ARM の SWD には CMSIS-DAP があり、任意の MCU 上の firmware が任意の host tool から使える。**RISC-V / CH32 にはそれが無い** |
| **上から** | **1 つの chip の周りで起きることを、1 つの時計に載せる計測器。** 書込・波形・相手役・電流・print が同じ時間軸に乗る |

**この道具は「口」と「装置」の 2 面を持つ。** 片面だけの製品は既にある(DIY probe は 10 種以上、安価な LA も、電流計も)。**両面を 1 本で持つものが無い。**

---

## 2. 何の問題を解くか — 3 つの壁

| 壁 | 中身 |
|---|---|
| **装置の壁** | CH32 に触るには**専用機を買う**必要がある。入手経路・送料・時間、そして**人数分** |
| **情報の壁** | 知識が 10 以上の project・vendor 資料・非公式解析に**分散**していて、**すでに装置を持っている人しか到達できない**。最初の 1 台を作りたい人が最も届かない |
| **能力の壁** | 装置を買っても、**線が見えない・相手役がいない・時計が別**。試験項目がまとめて着手できない |

**3 つは独立ではない。** 装置の壁があるから情報が集まらず、情報が無いから能力の壁が「そもそも何が足りないのか」の形で見えない。**だから 3 つ同時にしか崩せない。**

> 具体的な不満の一覧(P0a〜P0g / P1〜P15)は [harness-choices.ja.md](harness-choices.ja.md) ではなく**各 repo の要求カタログ**が正本。ここでは壁の形だけを固定する。

## 3. 他では解決できない強み

**まず「強みでないもの」を落とす。** ここを混ぜると差別化が説明できなくなる。

| 強みに見えるが、他で解決できるもの | なぜ強みでないか |
|---|---|
| 安く書ける | LinkE は安い。**価格は差にならない** |
| 波形が見える | 安価な LA がある。**むしろ帯域では負ける** |
| 電流が見える | 電流計がある |
| 手持ちの board で書ける | 既存 DIY probe が**個別には**やっている |

**残るのは 2 系統だけ。**

### S1 — 統合(1 台・1 つの時計)からしか出ないもの

| | 中身 |
|---|---|
| **意味イベントが推定でなく確定値** | 相手役を自分で演じているので、返した byte を知っている。**波形が粗くても byte 列は正しい**。波形から復元する装置では原理的に推定にしかならない |
| **バス事象を breakpoint にできる** | 「I2C の特定の書込が起きた瞬間に core を halt」。**debug probe と相手役が同一装置でないと作れない** |
| **自分が出した信号を自分で見られる** | 「線に何も出していない」を**証拠として出せる**。attach で target を汚さないことを主張できるのはこれだけ |
| **marker ピン無しで測定原点が作れる** | DMI 側と bus 側の**両方を持つ**装置だけができる。GPIO が 6 本の chip でも成立する |
| **絶対時間を比率に落とせる** | DUT の基準クロック出力を同じ窓で撮れば、**測定器の誤差と DUT の誤差を分離せずに済む** |

### S2 — 標準(1 つの口)からしか出ないもの

| | 中身 |
|---|---|
| **どの board でも同じ host から使える** | 既存 DIY probe は **MCU × transport × host tool が 1 対 1**。firmware は既にあるのに横展開できない。**足りないのは hardware ではなく口** |
| **個体が自分の能力を名乗る** | 「この probe は何ができるか」を**個体が申告する**。買う前・焼く前に判定でき、host が型番の表を持たなくて済む。**情報の壁への直接の解** |

### 中心にある主張

> **S1 は標準では解けない。S2 は hardware では解けない。**
> **この道具の強みは、hardware の統合と protocol の標準化を同時にやることでしか出ない。**

片方だけなら既存品の延長で終わる。**交点にしか無いものが強み**であり、**幅・方向性・PID の方針はすべてこの主張から導かれる**。

## 4. どこまでの幅を持つか

**段で並べる。**「誰が」ではなく「**どこまで欲しいか**」。

| 段 | 欲しいこと | 主に効く強み |
|:--:|---|---|
| **L0** | **とにかく書きたい。専用機を買わずに** | **S2** |
| **L1** | 書けて、**printf が見えれば十分** | S2 |
| **L2** | **離れた所に置きたい** | S2 |
| **L3** | 何台も同時に書きたい | S2 |
| **L4** | 止めて中を見たい(halt / step / GDB) | S2 |
| **L5** | **波形が見たい**(単体ロジアナとして) | S1 の入口 |
| **L6** | 書きながら見たい | **S1** |
| **L7** | **相手役が欲しい** | **S1** |
| **L8** | **計測器として使いたい**(障害注入・電流・bus 事象で halt) | **S1** |
| L9 | 無人で回したい(farm / 量産治具) | (運用) |
| L10 | 線そのものを解読したい | S1(自己観測) |

**L0〜L4 が S2 の領域、L5〜L8 が S1 の領域。** §3 の主張(交点にしか強みが無い)は、**幅の両端を切り離せない**ことを意味する。

| 区分 | 段 | 理由 |
|---|---|---|
| **中核** | **L0 〜 L8** | S1 と S2 の両方を含む最小の範囲。**片端を落とすと §3 の強みが消える** |
| **当初対応外** | **L9** | **device の話ではなく運用の話**。装置を増やす方向で、深める方向ではない |
| 中核だが順序は別 | L10 | 新規機能が要らない(L5 + 自己観測)。この repo の本業なので別に決める |

**段ごとの具体例・hardware の段差・今できるかは** [harness-choices.ja.md](harness-choices.ja.md) §1。

## 5. 現状の切り分け — **L0 / L1 に絞って**

**人数の山は L0 / L1**(書ければいい / printf が見えれば十分)。ここに絞って、**いま何がどこまで解けているか**を 3 つに分ける。

> **判定規則**(§3 の S1/S2 の裏返し): **chip 知識・アルゴリズム・表示は host 側 → ch32rv で解ける。時刻・状態・並列性・自発送信は probe 側 → host だけでは解けない。**

### 5.1 ① すでにある程度解決していること

| 課題 | いまの状態 |
|---|---|
| **LinkE 無しで書く firmware** | **10 種以上ある**(PicoRVD / Swindle / rvswdio / funprog / NHC-Link042 / ardulink / WebLink …)。**hardware 側は既に足りている** |
| **LinkE の firmware を全 OS で更新** | **ch32rv が実装済み**(`probe firmware update`、IAP 経路、実機で往復検証)。→ 「Windows 専用ツールしかない」という根拠は**もう成り立たない** |
| **識別・排他・exit code・capture / replay** | **ch32rv に実装済み**。要求として出す前に既にある(ライタ `0006` §13) |
| **probe 種別 / 版 / 能力の machine-readable 出力** | `probe info --json` / `capabilities --json` が既にある |
| **protocol の解読** | この repo。WCH-Link USB は大半 `verified`、DM/DMI は実装可。**「何を実装すればよいか」は分かっている** |
| ブラウザから書く道 | **V003 + rv003usb BL に限れば WebHID 実装が 2 つ**ある |
| probe 無しで書く道 | factory ISP / IAP(USB を持つ chip)。ch32rv に route がある |

→ **L0 は「実装が無い」のではない。「揃っていない」。**

### 5.2 ② ch32rv が対応すればある程度解決すること

**chip 知識が host 側にある**([設計原則 1](../protocols/dmi-bridge.ja.md))ので、**口を足すだけで既存 firmware がまとめて使えるようになる**。ch32rv には継ぎ目(`DtmAccess` trait)と枠(`ch32rv-probe-<name>`、**P2 で予約**、ardulink / funprog / NHC-Link042 が名指し)が既にある。

| 課題 | ch32rv が口を足すと |
|---|---|
| **P0c 横展開できない**(firmware × host が 1 対 1) | **解決する。** 手持ちの Uno / ESP32-S2 / STM32F042 / V003 単体が **Arduino IDE から使える** |
| **P0a 装置の壁** | **大きく軽くなる**(上の帰結) |
| **P0e / P13 printf が見えない** | **`monitor --source dmdata` は DM の DATA0/1 を DMI polling するだけで probe 非依存**。→ **口が繋がれば L1 が自動で付いてくる** |
| L4 GDB / debug | **host 側 GDB server** に寄せられる |
| **P6 プロセス起動が支配的**(1 board 30〜130 秒) | **セッション化は host 側の設計**。`Reader` 抽象に backend を足すだけ |
| P0g の一部(どの probe が何に対応しているか) | `capabilities --json` で**出せる**。ただし**手書きの表**になる(→ ③) |

→ **L0 と L1 の大部分は、firmware を 1 行も書かずに届く。** これが「まず ch32rv」の根拠。

### 5.3 ③ それでは解決できないこと

| 課題 | なぜ host だけでは無理か | 効く段 |
|---|---|---|
| **速度** | ardulink は `w`/`r` だけで **batch が無い**。64 KB を per-op で約 5 分。**口を増やしても速くならない** | **L0** |
| **2 線 target を手持ちの board で書く** | 既存 firmware で **2 線(RVSWD)を主張しているのは rvswdio と funprog だけ**。他は V003 / 1 線。**V20x / V30x / X03x を持っている人には道が細い** | **L0** |
| **firmware の保守が他人の手** | 成熟度は「very alpha」「experimental/RFC」「WIP/不安定」、**license も混在**。**probe 側のバグを ch32rv が直せない** | **L0 / L1** |
| **能力の申告(`caps`)が無い** | 既存 protocol に無いので、**host が型番の手書き表を持つしかない**。表は腐る。**P0g / 情報の壁の本体はここ** | **全段** |
| **event(probe → host の自発送信)** | 既存の口は全部 request/response。push 型の monitor が乗らない(polling は動くがコストがかかる) | L1 の一部 |
| **P0d リモート(L2)** | **transport は probe 側**。口をいくら増やしても、**IP を喋る firmware が無ければ届かない** | **L2** |
| L3 複数 / L5〜L8 | lane が無い / **時間軸が無く後付けできない** | L3 / L5 以上 |
| 識別の一律適用 | serial を持たない個体がある → fail-closed を当てられない | L3 / L9 |

### 5.4 L0 / L1 に絞ったときの結論

**新しい firmware(= 新しい protocol)が要る理由は、L0/L1 に限れば 4 つに絞られる。**

| # | 理由 | 性質 |
|---|---|---|
| **R-a** | **実用速度**(batch を持つ口が要る) | 既存の口の下限に張り付く問題 |
| **R-b** | **2 線 target への道** | 既存 firmware の被覆の穴。**§5.5〜5.7 で精度を上げた。③ の中で唯一「設計」ではなく「実装」の穴** |
| **R-c** | **保守を自分の手に**(バグ・chip 追加・timing を自分で直せる) | 他人の project に依存する問題 |
| **R-d** | **`caps`**(手書き表を捨て、個体が自分で名乗る) | **③ の中で唯一、L0 でも効く protocol 機能** |
| (R-e) | L2 に足を掛けるため | 幅を上に伸ばす前提 |

**逆に言えば、L0/L1 のためだけなら S1(統合)は要らない。** 統合の価値は L5 以上で出る(§3)。→ **§6 の方向性 A(標準先行)は、この 4 つを満たす最小の口を作ることに等しい。**

⚠ **R-d だけは性質が違う。** 速度・被覆・保守は「既存の口を置き換える」話だが、**`caps` は「情報の壁」への解**で、**幅をどこに取っても要る**(§7 で方向性に依存しない唯一の項目)。

### 5.5 chip 別に見ると、供給が V003 に偏っている

**既存 firmware の 1 線 / 2 線を数えると、はっきり偏っている**([probe-ecosystem](probe-ecosystem.ja.md) §1)。

| | 実装数 | 中身 |
|---|:--:|---|
| **1 線(V003 系)** | **10** | PicoRVD / rvswdio / funprog / ESP32-S3 / NHC-Link042 / Flipper / ardulink / WebLink / WCH 公式例 / UIAPduino 内蔵。**MIT が複数、browser flasher が 2 つ、bootloader、内蔵ライタ製品まである** |
| **2 線** | **3** | **Swindle**(RP2040 stable、**だが V20x/V30x のみ・GPL-3.0 系・probe 上 GDB 形**)/ **rvswdio**(最広だが **experimental/RFC**、V003 の software USB 上)/ **funprog**(2 線は source 段階) |
| **L103 / V103 / M030 / H41x** | **0** | **どの実装も主張していない** |

→ **V003 については、エコシステムはそれなりに揃っている。**(ユーザの指摘どおり。)**我々が L0 で足せる付加価値は小さい。**

**逆に 2 線側は、実装数 3 でも「stable かつ広い」ものが 1 つも無い** — Swindle は stable だが狭く GDB 形、rvswdio は広いが experimental。

> **⚠ 訂正(2026-09-07)。** 「主張なし」の series のうち、**L103 と V103 以外は未発売**で、**この道具でも救えない**(市場に無いものは書けない)。**実在する穴は L103 と V103 の 2 つだけ。** → **`R-b`(2 線の被覆)は「今の不満」としてはほぼ消え、差別化は `caps` / 速度 / 保守 / 上の段(S1)に移る。** 詳細は [harness-scope-decisions §2.2](harness-scope-decisions.ja.md)。原因は **`ch32-device-data` に入手可否の列が無い**こと(同 §2.2b、データ依頼の候補)。

### 5.6 V003 の役割が変わる — **顧客ではなく、苗と制約**

供給が揃っているなら、V003 を「解決すべき対象」として見るのはもう合わない。**3 つの役割に分けたほうが正確**:

| 役割 | 評価 |
|---|---|
| **target としての V003**(V003 に書きたい) | **優先度は低い**。既に揃っている(§5.5)。ここに労力を割いても差にならない |
| **probe としての V003**(V003 を書込器にする) | **価値が高い**。**$0.1 の chip が probe になる**ことは rvswdio が実証済み。**連鎖 bootstrap の苗**([ecosystem](ecosystem-any-hardware.ja.md) §2)= 「1 台目さえあれば増える」の起点 |
| **制約としての V003**(V003 でも動く protocol にする) | **設計を締める**。software USB / 2 KB RAM / BL 1,920 B。**ここに入るなら他は全部入る**。ただし**入れるために幅を狭めるなら本末転倒** |

→ [harness-choices.ja.md](harness-choices.ja.md) の**軸 B(V003 を含めるか)は、この 3 役割で答えが違う**。「V003 を諦める」が意味するものを役割ごとに分けないと選べない。

### 5.7 需要と供給がずれている

- **供給は最安 chip に偏る**(V003 は probe 側も target 側も最安)。
- **需要はそこだけではない** — X035 は USB-PD で採用が広がり、V203 は STM32 代替、V307 は高機能用途。
- **LinkE + ch32rv なら 24 series 全部書ける**(probe 経路 `verified`)。→ **穴は「LinkE を買わずに 2 線を書く」ところだけ。**

**これで §5.4 の R-b の性質が変わる。**

| 版 | `R-b` の書き方 |
|---|---|
| 初版 | 「2 線 target を手持ちで書く道が細い」 |
| 第 2 版 | (i) stable かつ flashing CLI 形の 2 線 probe が無い(Swindle は GDB 形 + GPL-3)/ (ii) L103 / V103 / M030 / H41x はどの実装も主張していない / (iii) X03x は rvswdio のみ(experimental) |
| **第 3 版(現行)** | **⚠ 未発売を除くと実在する穴は L103 と V103 の 2 つだけ。** → **残るのは (i)(iii) の「質」の問題**(stable でない / GDB 形 / GPL-3 / experimental)**であって「量」の問題ではない** |

**R-b は ③ の中でも性質が違う**(「2 線の phy を誰かが書く」という実装の穴で、ch32rv 側では埋まらない)。**ただし訂正後は規模が小さい** — 実在する穴が 2 series なので、**`R-b` 単独では firmware を書く理由として弱い**。→ **理由の重心は `R-a`(速度)・`R-c`(保守)・`R-d`(`caps`)、そして上の段(S1)に移る。**

→ 「口を増やす作業(ch32rv の backend)」と「2 線の phy を書く作業(新 firmware)」は**別物**だが、**訂正後は後者の規模が小さい**。**方向 A の主戦場は「series の被覆」ではなく「`caps` と速度と保守」**になる。

### 5.8 V003 の境目 — **BL は捨て、APP は取る**(方向の候補。**結論ではない**)

§5.6 の 3 役割は、**もう 1 軸(firmware がどこに住むか)を掛けると更にはっきりする**。

| | **APP 領域**(user flash 16 KB) | **BOOT 領域**(1,920 B) |
|---|---|---|
| **probe**(他の chip を書く) | **◎ 対応したい。** basic HID ≈ 2 kB + protocol が 16 KB に余裕で入る。rvswdio が実証済み | — (probe を BOOT に置く理由が無い) |
| **target**(書かれる側) | — | **既存で足りる**(§5.5)。優先度低 |
| **self**(同一 chip が自分を書く) | app 側 updater は既に実証済み(BOOT 領域書換) | **✗ 捨てる。** rv003usb BL + B003 が既にあり、**置き換える利得が無い** |

**「捨てる」の根拠は既に出ている** — [v003-bootloader-replacement.ja.md](v003-bootloader-replacement.ja.md) の結論そのもの: 標準 BL は**既に stub 実行型**で、**1,920 B に対して実サイズがほぼ 1,920 B**、**host 実装が 3 つある**。入れ替えは「完全上位」の 6 条件を満たさない。

#### この境目を引くと 3 つ楽になる

| # | 楽になること |
|---|---|
| 1 | **Nano profile の主な存在理由が消える。** [harness-choices](harness-choices.ja.md) §3 の Nano は「V003 の BL 1,920 B に入れるため」に出した案だった。**APP なら 16 KB あるので Core が入る。** → Nano が要るのは **AVR / 8 bit 級のため**だけになり、それは **ardulink 互換モードで足りるかもしれない**(別の解がある) |
| 2 | **他人の PID を名乗る必要が消える。** BL に相乗りしないなら `1209:B003` を名乗る話が消え、**N4 / K3 の懸念がそもそも発生しない** |
| 3 | **BL と APP が同じ chip で共存できる。** BL は B003(cnlohr の project)、APP は我々の protocol。**mode ごとに ID が別なのは §4.3 と整合**で、無理が無い |

#### 代わりに残る問い

**APP としての V003 を、どの transport で host に繋ぐか。**

| 案 | 中身 | 効く制約 |
|---|---|---|
| **software USB(HID)** | rvswdio と同じ形。**挿すだけ**が成立する | **K5 が残る**(low-speed は bulk が無く HID 固定)。**自前 PID が要る**。Windows 不安定・ケーブル長敏感の実地報告あり(UIAPduino) |
| **UART**(V003 の USART 1 本を host link に使う) | ardulink 形。**PID が要らない**([K6](harness-choices.ja.md)) | USART が塞がるので **target の serial を橋渡しできない**。USB-serial 変換が別に要る |

→ **K5(HID 固定)の縛りは「BL のため」ではなく「APP の V003 を USB で使うため」に移る。** [choices](harness-choices.ja.md) の軸 A / B はこの形で読み直す必要がある。

#### 用語が未定(整理が要る)

いま 2 つの別物が同じ語で呼ばれている。**呼び分けが決まらないと `caps` の設計も決まらない**。

| 概念 | 中身 | 現状の呼び方 |
|---|---|---|
| **別 chip・同一基板** | probe MCU と target MCU が別の chip で、同じ board に載っている | 「内蔵ライタ」「built-in」「ビルドイン」 |
| **同一 chip** | 同じ chip が自分自身を書く(BOOT ↔ user 領域) | 「セルフ」「self-update」「in_place」 |

⚠ **[builtin-probe-and-self-update.ja.md](builtin-probe-and-self-update.ja.md) はファイル名で両者を並べているが、本文では `attach`(lane の向こう側 = external / onboard / socket / self)と `self_update`(自分をどう書くか)という別の 2 軸で扱っている。** **概念は分かれているが、名前が揃っていない。** → 取りまとめの第 2 部で語彙を固定する対象。

## 6. 方向性の候補(**まだ選ばない**)

**幅は L0〜L8 で取る**としても、**どちらの端から作るか**で性格がまるで変わる。

| | **方向 A: 標準先行** | **方向 B: 統合先行** | **方向 C: 一本化** |
|---|---|---|---|
| 最初に出すもの | **口**(L0〜L4)。**§5.4 の R-a〜R-d を満たす最小の口**。既存 firmware も含めて繋がる | **1 台の完成品**(L5〜L8) | **仕様を先に固め、両端を同時に** |
| 強みの出方 | **S2 が先。S1 は後** | **S1 が先。S2 は後** | 両方だが遅い |
| 届く人数 | **最大**(手持ちで始められる) | 少数(道具を作れる人) | — |
| 失敗の形 | 「速くもないし何も見えない口」が普及して、上に登る動機が消える | 「作った人しか使えない立派な装置」で終わる。**情報の壁が残る** | **仕様が固まる前に要求が変わる**。手戻りは無いが出荷が遅い |
| 検証の初速 | 低(繋がるだけ) | **高**(L5 は target すら不要で測れる) | — |
| 相手 repo への影響 | ライタ(口を増やす)が主役 | コア(試験が動く)が主役 | 全 repo が待つ |

**判断に要るのは 2 つだけ**:

1. **S1 と S2 のどちらが「他では解決できない」度合いが高いか。** §3 は両方だと言っているが、**先に出したときの取り返しやすさが違う**(A は後から S1 を足せる。B は後から S2 を足すと既存実装の互換が問題になる)。
2. **人数を先に取るか、深さを先に取るか。**

## 7. 方向性が決まると導かれるもの

**逆に言えば、これらを方向性より先に決めてはいけない。**

| 導かれるもの | A(標準先行)なら | B(統合先行)なら | C なら |
|---|---|---|---|
| **PID の方針** | 口の互換が最優先 → **PID を消費しない transport(既存 bridge の UART / IP)を主にできる**。自前 USB は後回し | **1 台の silicon が決まる** → その vendor program で足りる(RP2040 なら `0x2E8A`)。**pid.codes を使わずに済む可能性** | **1 つの ID で全段を名乗る**必要が出て、制約が最も厳しく効く |
| **profile の下端** | **下端を深く取る**(8 bit 級・BL まで)必要が出る | 下端は後で決めればよい | 最初に決めないと進めない |
| **V003 を含めるか** | **含める動機が強い**(最安の入口) | 当面外してよい | 最初に決める |
| **transport の主従** | UART / IP が主、自前 USB が従 | 自前 USB が主 | 両方を仕様で覆う |
| **作る順序** | ライタの backend → 口の仕様 → 上の段 | L(キャプチャ)→ WL → エミュ | 仕様 → 実装 |
| **先に裁くべき相反** | **C-12**(DMI をどの段階で要求するか)。下の段は DMI が薄い | **C-1 / C-4 / C-6**(模型・帯域・窓) | 全部 |

**選択肢の中身は** [harness-choices.ja.md](harness-choices.ja.md)。**そこで決めるのではなく、方向が決まってから選ぶ。**

## 8. やらないこと(永久の非目標)

**当初対応外**(後で足しうる)は §4 の区分。ここは**設計としてやらないと決めるもの**で、相反の裁定でここを越える要求は落とす。

⚠ **2026-09-07**: **N9(独自 PID で HID なしを禁止)を一度立てたが、非目標から降ろした。** 禁止の根拠が 2 点で崩れた — (1) **不変条件が host の分岐を消していない**(UART / IP / `MSC のみ` にはどうせ HID が無く、serial transport は既に実装が要る)、(2) **禁止すると「BL でも同じ protocol を喋る」という狙いの中心(hardware USB の BL が CDC で dmibridge を喋る形)を弾く**。→ **強い推奨に格下げ**。詳細は [channels §6h.1h](harness-channels.ja.md)。**この一連の議論で新たな禁止は生まれなかった。**

| # | 非目標 | 理由 |
|---|---|---|
| **N1** | **連続ストリーミングの汎用ロジアナ** | 帯域では専用品に負ける。強みは §3 の S1 であって帯域ではない |
| **N2** | サイクル精度のシミュレータ | 実機を測る道具。**ベンチが範囲外と明示している側** |
| **N3** | **LinkE の互換品** | 目標は **LinkE が要らない場面を増やす**こと。USB protocol 互換も VID の詐称もしない |
| **N4** | 他人の PID / 共有 PID を firmware が名乗ること | **この repo に衝突の実例がある**(LinkE の IAP と factory ISP が同じ ID)。host が他人の protocol を喋るのは別問題(可) |
| **N5** | 同梱アップローダになること | コアの既定(同梱は 1 本に絞る)を動かさない |
| **N6** | 全 series を書ける書込器としての完成 | 線層が `attested` 止まり。**そこは L10 で先に埋める** |
| **N7** | host からバス転送を返す形 | SPI / UART は待たせる手段が無く原理的に不可 |
| **N8** | chip 固有知識を firmware に入れること | [設計原則 1](../protocols/dmi-bridge.ja.md)。**ただし「演じるデバイスの知識」は別問題**(相反 C-1) |

## 9. 判定 — 本書の各項目は無理なく対応できるか

**判定の対象は本書の項目**(機能 `F`、強み `U`、段 `L`、不満 `P`、非目標 `N`)。**feature 単位の判定は細かすぎた**ので([harness-requirement-triage.ja.md](harness-requirement-triage.ja.md))、こちらを正本にする。

**語彙**: `◎` 無理なく / `○` 段階的に(一部が安い) / `△` 条件付き(前提が要る) / `✗` 無理あり / `済` 既存 + ch32rv。
**依存**は [harness-scope-decisions.ja.md](harness-scope-decisions.ja.md) の決定軸。

### 9.1 機能(§3 の F0〜F7)

| | 機能 | 判定 | 依存 | 中身 |
|---|---|:--:|---|---|
| **F0** | 共通 protocol(標準の口) | **◎** | D11 / D6 | **作ると決めれば安い**。互換モードは 1 byte 判別で同居できる |
| **F1** | 観測(capture) | **△** | **D5** / D1 | **RP2040 級が前提**。作らない選択もある(→ 9.2 が全部消える) |
| **F2** | 相手役(emulation) | **○** | D5 | **UART×2 / SPI slave / I2C 2 アドレスは安い**(hw 周辺)。**多アドレス I2C だけ ✗** |
| **F3** | 刺激と障害注入 | **◎** | (F2) | GPIO / PWM / hw UART の break は安い。**バス注入は F2 に従属** |
| **F4** | **debug 線(DMI)** | **◎** | **D2 / D3** | **core そのもの。ここだけで L0/L1/L3/L4 が立つ** |
| **F5** | アナログ | **○** | D9 | ADC 3〜4ch は安い。**電流は外付け部品(シャント + INA)** |
| **F6** | 1 つの時間軸 | **△** | **D5** | **F1 が無いと成立しない** |
| **F7** | 運用 | **◎/△** | D1 / D7 | 大半は host 側。watchdog / self-test は安い。**IP と composite だけ条件付き** |

→ **F0 + F4 が核**。この 2 つだけで §9.3 の L0/L1/L3/L4 と §9.4 の不満の過半が動く。

### 9.2 統合からしか出ない強み(§3 の U1〜U5)

| | 強み | 判定 | 依存 |
|---|---|:--:|---|
| **U1** | 意味イベントが確定値 | △ | **F2 + F6** |
| **U2** | cross-domain trigger | △ | **F1 + F4** |
| **U3** | marker 無しで測定原点 | △ | **F1 + F4** |
| **U4** | **自己観測** | **△ だが安い** | **F1 + F4**。窓に debug 線を置くだけ |
| **U5** | **絶対時間を比率に**(MCO) | **△ だが安い** | **F1**。1ch 消費のみ |

> **⚠ U1〜U5 は全部 F1(capture)に依存する。** つまり **D5 で「capture を作らない」と決めると、S1(統合の強み)が丸ごと消え、この道具は「標準の口」だけになる。** §3 の「交点にしか強みが無い」という主張は、**判定すると D5 一点に集約される。**

### 9.3 段(§4 の L0〜L10)

| 段 | 判定 | 依存 | 中身 |
|:--:|:--:|---|---|
| **L0** | **◎** | **D2** | 既存 + ch32rv でほぼ届く。**差は実在する穴 2 series(L103 / V103)と、`caps` / 速度 / 保守** |
| **L1** | **◎** | — | **`SerialDMDATA` は probe 非依存**。F4 があれば付いてくる |
| **L2** | **△** | **D1** | **transport は probe 側**。Wi-Fi 機の build が要る |
| **L3** | **◎** | D1 | `lane` は既にヘッダにある。**SM を増やすだけ**(命令メモリは共有) |
| **L4** | **◎** | — | **GDB server は host 側** |
| **L5** | **△** | **D5 / D1** | RP2040 級。**target 不要で始められる** |
| **L6** | **△** | D5 | L5 + F4 |
| **L7** | **○** | D5 | 器は安い。**多アドレス I2C と模型の統合が ✗** |
| **L8** | **△** | D5 / D9 | F5 の電流 + F1 |
| L9 | **当初対応外** | — | 運用の話(§4) |
| **L10** | **△ だが安い** | D5 | **U4 で足りる。新規機能が要らない** |

### 9.4 不満は解消できるか(§2 の P0a〜P0g / P1〜P15)

| | 不満 | 判定 | どう解消するか |
|---|---|:--:|---|
| P0a | 専用機を買わないといけない | **◎** | L0 |
| P0b | ARM なら手持ちで済んだ | **◎** | **F0** |
| P0c | 10 種以上あるのに横展開できない | **◎** | **F0 / D11**(host が吸収でも解ける) |
| P0d | リモートに 2 台要る | **△** | L2 / D1 |
| P0e | printf が見えない | **◎** | F4 → host |
| P0f | **情報が持っている人にしかない** | **○** | **`caps` で「何ができるか」は解ける。知識の分散そのものはこの repo の仕事** |
| P0g | どの probe が何に対応しているか | **◎** | **`caps`** |
| P1 | 波形が見えない | **△** | **D5** |
| P2 | 相手役がいない | **○** | F2 |
| P3 | attach で target を汚す | **◎** | **F4(passive attach)** |
| P4 | クロックツリーを検証できない | **◎** | P3 の帰結 |
| P5 | 1 往復が遅い | **◎** | batch |
| P6 | プロセス起動が支配的 | **済** | host 側 |
| P7 | probe が固まる | **◎** | watchdog + 自作の品質 |
| P8 | firmware の版が自分の手に無い | **◎** | UF2。**ch32rv が既に半分解消** |
| P9 | USB port が足りない | **△** | composite(D7) |
| P10 | 静かに緑になる | **済** | host 側のカバレッジ報告 |
| P11 | host backed が成立しない | **◎** | F2 の設計方針(器は probe 内で完結) |
| P12 | 制御チャネルが USART を潰す | **◎** | F4 → dmdata / RTT |
| P13 | debug 出力 3 経路がツールに縛られる | **◎** | 同上 |
| P14 | **線層が未検証** | **△** | **U4**(L10) |
| P15 | host で通るのに実機で落ちる | **△** | F2 + F6 |

**◎ が 13 / ○ が 3 / △ が 6 / 済 が 2。** → **不満の側から見ると、`△` の 6 件は全部 D5(capture)か D1(board)か D7(PID)に依存**していて、**それ以外は無理なく解消できる。**

### 9.5 非目標は妥当か(§8 の N1〜N8)

| | 非目標 | 判定 | 備考 |
|---|---|:--:|---|
| N1 | 連続ストリーミングの汎用 LA | **妥当** | 強みは S1 であって帯域ではない |
| N2 | サイクル精度のシミュレータ | **妥当** | ベンチが範囲外と明示している側 |
| N3 | LinkE の互換品 | **妥当** | |
| N4 | 他人の PID / 共有 PID | **妥当**(むしろ強化) | この repo に衝突の実例 |
| N5 | 同梱アップローダ | **妥当** | |
| **N6** | **全 series を書ける書込器としての完成** | **⚠ 表現を見直す** | 「線層が `attested` だから遠い」と書いたが、**D2 で「穴の 10 series を取る」と決めるならそれは "全 series 完成" とは別の話**。**「全 series」を非目標にすると D2 と矛盾しうる** |
| N7 | host からバス転送を返す | **妥当** | SPI/UART は原理的に不可 |
| N8 | chip 固有知識を firmware に | **妥当** | 「演じるデバイスの知識」は別(C-1) |
| ~~N9~~ | ~~独自 PID で HID なし~~ | **非目標から降ろした**(2026-09-07) | **禁止の根拠が崩れた**(host の分岐を消さない / BL の中心形を弾く)。→ **強い推奨**。**推奨構成は `HID + Vendor + CDC ×n`**(→ [channels §6h.1h](harness-channels.ja.md)) |

### 9.6 判定の要約

1. **`F0`(標準の口)と `F4`(debug 線)だけで、段の L0/L1/L3/L4 と不満の 13 件が動く。** ここは**依存が D2(どの series)だけ**で、他の軸を待たずに判断できる。
2. **`F1`(capture)が最大の分水嶺。** **`U1`〜`U5` の全部、段の L5〜L8 と L10、不満 6 件のうち 4 件**がここに依存する。→ **D5 を決めることが、この道具の性格を決める。** ⚠ **D2 の訂正(実在する穴は 2 series)で series 被覆が差にならなくなった分、`D5` の重みが相対的に上がった。**
3. **`F2`(相手役)は段階的**。hw 周辺で足りる範囲(UART×2 / SPI slave / I2C 2 アドレス)は安く、**多アドレス I2C だけが壁**。
4. **不要と判定したものは無い。** ただし **N6 の表現は D2 と衝突しうる**ので見直す(§9.5)。**落とす候補は [harness-scope-decisions §4](harness-scope-decisions.ja.md) 側に列挙した。**

## 9b. 論点の棚卸し(2026-09-07)

**議論が広がる一方だったので、閉じたものを閉じる。**

### 閉じた(争点が無い)

| 論点 | なぜ閉じたか |
|---|---|
| **書込 / デバッグ / print を DMI で通す** | **`(addr7, data32, op2)` に独立 3 実装 + 標準が収束**(RISC-V Debug Spec / WCH-Link `DmiOp` / BMP remote / minichlink 抽象)。→ [channels 補足 J](harness-channels.ja.md) |
| **chip 知識を host に置く** | 同じ収束の帰結。BMP の hosted 形も target 層を PC 側に置いている |
| **`caps` で能力を申告する** | **幅をどこに取っても要る**(§9.6-4)。PID の節約と機能の可視化を同時に解く |
| **monitor 3 経路(SDI / DMDATA / RTT)を probe 非依存にする** | **全部 DMI read**。host 側で解ける |
| **1 線 / 2 線の差を PC 側に出さない** | 既に仕様がそうなっている(configure/DMI/flash が同一) |

### 各論(大枠の判断には要らない)

| 論点 | 決まる場所 |
|---|---|
| CDC の本数 / 割当 / 混合 | **`caps` の申告値 + 実行時 `configure`**。→ [channels 補足 I](harness-channels.ja.md) |
| `batch` の op 集合、busy 再試行の所在、timeout、`max_inflight` | draft にある。実測で詰める |
| `cmd` 番号範囲、event の番号 | 実装時 |
| `bcdDevice` の BCD 分割の細部 | 実装時 |

### 本質的に残っている(**大枠の判断**)

| # | 論点 | 何が決まるか |
|---|---|---|
| **1** | **`trace`(波形)を作るか** | **`U1`〜`U5` の全部**、段の L5〜L8 と L10、不満 6 件のうち 4 件。**この道具の性格そのもの**(§9.6-2)。⚠ **2026-09-07: 論点 3 が上流かもしれない** — **`emu` を作ると capture の要求が下がり**(decode 済みデータが 1/1000 の帯域で得られる)、**trigger の難所も `emu` が引き取る**(protocol 条件は PIO では作れないが emu なら自然に取れる)。→ [virtual-if §10 / §11](harness-virtual-if.ja.md) |
| **2** | **時刻を持つ 4 つ(波形 / 意味イベント / DMI 実行印 / ADC)を 1 本の列にまとめるか** | **`U1`(意味イベントが確定値)の成否**。→ [channels §1.3](harness-channels.ja.md) |
| **3** | **相手役(`emu`)をどこまで持つか** | 器だけ / 模型も積む。**PIO I2C slave が通るかに依存**。⚠ **論点 1 より上流の可能性**(→ 上記) |
| **4** | **どの MCU を probe にするか** + **`bcdDevice` major の割り方** | 到達できる段 / PID の消費 / 拡張余地 |
| **5** | **どの target series を覆うか** | **実在する穴は L103 と V103 の 2 つ**。残り 9 は未発売 |
| **6** | **方向性 A / B / C**(標準先行 / 統合先行 / 一本化) | 何を最初に出すか(§6) |
| **7** | **既存 firmware との関係**(互換モードを持つか) | **我々の host が完成する前に価値が出るか** |

→ **7 つ。** うち **1 が最上流**(他の多くがここに依存)、**5 は選ぶだけ**(データは揃った)、**7 は今すぐ決められる**(他に依存しない)。
