# DUT harness — 仮想 IF の分離(何を DMI に載せ、何を別にするか)

状態: **draft / 分析**。**結論は出さない**。物理 IF(probe ↔ PC)は [harness-channels.ja.md](harness-channels.ja.md) で整理済みで、本書はその**内側**、つまり **1 本の物理 IF の中でどう論理的に分けるか**を扱う。

**扱わないこと**: **時刻の付与と相関**(複数 source を同じ時間軸に載せるか)は [定義 §9b](harness-tool-definition.ja.md) の**残る論点 2**。本書で言う「到着順」は **1 本の列に入れれば順序が保たれる**という多重化の性質のみを指し、**timestamp を打つ話ではない**。

---

## 1. 用語 — **形は 2 つしかない。理由は「誰が発生タイミングを知っているか」**

**通信の形を分類する軸を先に導く。** 恣意的な分類を避けるため、**「いつ送るべきかを知っているのはどちらか」**だけで切る。

| 知っているのは | どうなるか | 仕様の語 |
|---|---|---|
| **host** | host が送り、probe が答える。**host は「答えが来るまで」を知っている** | **`req` / `resp`**([§3](../protocols/dmi-bridge.ja.md) `type = 0x00` / `0x01`) |
| **probe だけ** | **host は聞くべき時刻を知らない**ので、聞くと必ず遅れるか空振りする。→ **probe が要求なしに送る** | **`event`**(`type = 0x02`、`tag = 0x00`) |

→ **形は 2 つ。**「push」という語は使わない(**仕様が `event` と呼んでいる**)。

**なぜ `event` が必要か**(= host が polling で代替できない理由): target が print した byte、電源が落ちた、線が切れた — **いずれも「起きた瞬間」を probe しか知らない**。host が polling すると **(a) 周期の分だけ遅れ、(b) 周期の間に複数起きると取りこぼし、(c) 何も起きていないときも往復が発生する**。→ **event は最適化ではなく、正しさの要件**。

### 1.1 `stream` は第 3 の形ではない — **`event` の高頻度な場合**

波形サンプルは `event` と**構造が同じ**(probe が発生を知り、要求なしに送る)。違うのは**頻度**だけ… **ではなく、1 点だけ本質的に違う**:

| | 単発の `event` | `stream` |
|---|---|---|
| 例 | 「線が切れた」「byte が来た」 | 波形サンプル、ADC |
| **1 件だけで意味を持つか** | **持つ** | **持たない**。**「連続していること」自体が情報** |
| **欠落したときに何が起きるか** | **その 1 件が無いだけ** | **無音 1 µs と「1 µs 分落とした」の区別がつかない** → **残りの解釈まで壊れる** |

→ **`stream` に必要な追加要件は「連番」**。**単発 `event` には連番が要らないが、`stream` には要る。** これが §6 で挙げる仕様の穴の根拠。

## 3. なぜ分離が必要になるのか — **輻輳したときの 2 つの現象**

**混雑していなければ 1 本で足りる。** 分離が要るのは**輻輳したとき**だけで、そのとき起きる困りごとは **2 つに絞られる**。

### 3.1 現象 1 — **列の占有**(head-of-line blocking)

**1 本の FIFO では、先に入ったものが送り終わるまで後続は待つ。**

| 状況 | 待ち時間 |
|---|---|
| HID(64 B / 1 ms)で **1024 B の波形 datagram** が先に入っている | **16 ms**。後続の `dmi` は **1 ms のはずが 16 ms 待つ** |
| CDC(~1 MB/s)で **MB 級の `emu` preload**(#18)が流れている | **数秒**。その間 `dmi`(#4)が完全に止まる |

⚠ **`max_inflight` の既定が 1**([caps §5.2](../protocols/dmi-bridge.ja.md))なので、**req/resp 側は仕様上そもそも 1 件ずつ**。#18 のような大物を同じ列に置くと、**待ちが単なる遅延ではなく完全停止になる**。

→ **効くのは「1 件の大きさ × 頻度」= 列を占有する時間**。**帯域の桁が違うものを混ぜると、小さい方が待たされる。**

### 3.2 現象 2 — **運命の共有**(overflow したとき誰が捨てられるか)

**1 本の FIFO が溢れたとき、何を捨てるかを選べない。** そして **捨ててよいものと捨ててはいけないものが、正反対の性質で並んでいる**:

| | **落とさずに済ませられるか** | **失ったら取り返せるか** |
|---|:--:|:--:|
| **波形 / ADC**(#14 #15) | **✗ 不可能**。**帯域が原理的に足りない**ので、必ずどこかで間引く | **○ 撮り直せる**。trigger をかけ直せばよい |
| **target serial / 意味イベント / 通知**(#9 #10 #12 #16 #24) | **○ 容易**。**11.5 kB/s なので帯域は足りている**。詰まるのは**他が食っているときだけ** | **✗ 不可能**。**target は同じ print を繰り返さない**。電源断は一度きり |
| `log`(#11) | ○ | ○(**どちらでもよい**) |

→ **上 2 行が完全な裏返しになっている。**

> **同じ FIFO に入れると、「落とさなくて済んだはずのもの」が「必ず落ちるもの」の溢れに巻き込まれて落ちる。**

⚠ **これが分離の最も強い理由。** 「片方が lossy だから」ではなく、**回復可能性と回避可能性が逆向きだから**。

### 3.3 分離の理由に**ならない**もの

| 挙げたくなる軸 | なぜ理由にならないか |
|---|---|
| **`mtu` を超える**(#18 #19 #23) | **分離ではなく断片化で解ける**。断片化した大物が列を占有する点は**現象 1 に帰着**する。→ **別枠の「足りない機能」**(§6) |
| req/resp か event か | **`type` で既に区別できている**。**別の列が要るのは現象 1 のせい**であって、形そのものではない |
| latency 要求 | **優先度で解ける**(列を分けなくてもよい) |
| 発生率 | 単体では無害。**現象 1 の中に「× 頻度」として入っている** |
| 方向 | `type` で足りる |

→ **分離を強制するのは現象 1 と 2 の 2 つだけ。**

### 3.4 逆に**統合を要求する**もの

**到着順**: **1 本の列に入れれば、相対順序がタダで保たれる。** 分けると失われ、**復元するには連番か時刻が必要になる**(時刻は本書の範囲外 = 論点 2)。

→ **これが分離の唯一のコスト**であり、**案の trade-off の核**。

## 4. グループ化の案 — **現象 1 / 2 にどう答えるか**

### 案 A — **全部 1 本、到着順**

| | |
|---|---|
| 現象 1 | **解かない**。波形が `dmi` を待たせる |
| 現象 2 | **解かない**。溢れたら区別なく落ちる |
| 得 | **どの物理 IF でも成立**。**到着順がタダ**。**実装が最小**(現行 L1/L2 のまま) |
| 成立条件 | **#14 #15 を入れないなら、現象 1 も 2 も起きない**(#9 の 11.5 kB/s は HID の 64 kB/s に十分収まる) |

⚠ **単線 transport(既存 bridge UART / CDC ×1 / HID のみ)では、案 A 以外を選べない。** → **A は「選ぶ案」ではなく最小構成での必然。**

### 案 B — **2 分: req/resp と event**(**現行仕様**)

| | |
|---|---|
| 現象 1 | **部分的に解く**。event が req の `tag` を汚さないが、**同じ物理 IF を共有するので占有は残る** |
| 現象 2 | **解かない**。**event 列の中で #14(必ず落ちる)と #9 #12 #16 #24(落としてはいけない)が同居する** |
| 得 | **既に実装されている**。**`uart_data.dropped` で「黙って落とさない」を列の内側で実現している** |

### 案 C — **3 分: control / 落としてよい event / 落としてはいけない event**

**§3.2 の表の 3 行がそのまま 3 本になる。**

| | |
|---|---|
| 現象 1 | **解く**(大物を分離できる) |
| 現象 2 | **解く**(**溢れたとき波形だけを捨てられる**)。**最も本質的な軸で切っている** |
| 損 | **列が 3 本要る**。**単線では 1 本の帯域を分け合うだけなので、現象 1 は解けても現象 2 しか実効がない** |
| 効く条件 | **物理 IF が複数あるとき**(Vendor bulk を別 endpoint / IP で port 追加 → [channels §6c](harness-channels.ja.md)「IP なら別ラインがほぼ無料」) |

### 案 D — **channel ごと完全分離 + 優先度**

| | |
|---|---|
| 現象 1・2 | **両方解く**。**channel ごとに背圧と優先度を宣言できる** |
| 得 | **host が「今は波形を止めて serial だけ」と選べる** |
| 損 | **scheduler が probe 側に要る**(小さい MCU で重い)。**到着順が完全に失われる**(§3.4) |

## 5. 現行仕様が今の形になっている理由

**「なぜそうなっているか」を仕様の記述から起こす。**

| 選択 | 理由(仕様が述べているもの) |
|---|---|
| **`type` で req/resp/event を分ける** | **event は `tag` を持てない**(採番するのは req 側)。分けないと対応付けが壊れる |
| **`lane` をヘッダに置く**(引数にしない) | **firmware がコマンドを解析する前に phy へ振り分けられる**。**引数にすると `batch` ごとに分岐が入り、event が lane を名乗れない** |
| **`uart_data` に `u16 dropped`** | **黙って落とさない**(原因不明の欠落を防ぐ)。→ **案 B の中で現象 2 に部分的に答えている** |
| **`batch` に `poll` がある** | **BUSY 待ちが往復を作らない**。#4 の ~150K 往復問題への直接の対策 |
| **busy 再試行を probe が吸収** | **host を単純に保つ** |
| **`max_inflight` 既定 1** | 同じ理由。⚠ **その代償が §3.1 の「待ちが完全停止になる」** |
| **critical section 中は event をキューに積む** | **線の bit 操作を割込みで乱せない**(software USB の ~40 cycle 制約と同種の問題)。⚠ **その代償が §6 の「1 MB/s では即溢れる」** |
| **`autopoll` がある** | **SDI print の往復を probe 内に閉じ込める** = #21 を req から event に変える仕組み。**既に前例がある** |

→ **現行仕様は「案 B + 現象 2 への部分的な答え(`dropped`)」**。**#14 を持たない前提では一貫している。**

## 6. 現行仕様に足りないもの(**#14 を入れる場合**)

| 穴 | 中身 | 由来 |
|---|---|---|
| **event に連番が無い** | `tag = 0x00` 固定。**欠落の検出手段が `uart_data.dropped` だけ** | **§1.1**: `stream` は「連続していること自体が情報」なので**連番が必須** |
| **event キューが小さすぎる** | `caps.event_queue` = u16 → **最大 65,535 B**。**1 MB/s では 0.065 秒分** | §5 の「critical section 中はキュー」と #14 の帯域が両立しない |
| **critical section の規約が stream に合わない** | 線操作中に停止 → 即溢れる | 同上 |
| **`mtu` 超えの転送手段が無い** | #18 #19 #23 が 256〜1024 B に収まらない | §3.3。**`info` の `u16 offset` 方式が既に前例** |
| **背圧 / overflow の通知が無い** | #24 が存在しない | §3.2。**捨てた事実を伝える経路が要る** |
| **`max_inflight` = 1** | MB 級の #18 中は #4 が完全に止まる | §3.1 |

⚠ **いずれも「#14 を作る」と決めてから直す項目。** **作らないなら現行のままで穴ではない。**

## 7. 何で決まるか

| # | 判断 | 依存先 |
|---|---|---|
| **1** | **#14(波形)を作るか** | **[定義 §9b](harness-tool-definition.ja.md) 残る論点 1**。**作らないなら案 B のままで足りる**(§4) |
| 2 | #16(意味イベント)を持つか | 残る論点 3(`emu` をどこまで) |
| 3 | 時刻を付けるか | **残る論点 2**(本書では扱わない) |
| 4 | 物理 IF が複数あるか | [channels §6h](harness-channels.ja.md) の推奨構成(`HID + Vendor + CDC`)なら **Vendor に別 endpoint を持てる** |

→ **判断 1 が決まらないと、案 C / D を評価する意味が無い。**
