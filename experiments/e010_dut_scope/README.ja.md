# E010 ハーネス: 1 ファイルに複数のテスト関数を置けるか

規則: [../README.ja.md](../README.ja.md) / 台帳: [../LEDGER.ja.md](../LEDGER.ja.md) / 前段: [E001](../e001_smoke_host/README.ja.md) 事実 2

## 問い

**1 つの実験ファイルに複数のテスト関数を置けるか。置けないなら、その制約は何によるものか。**

[E001](../e001_smoke_host/README.ja.md) 事実 2 は「DUT はテスト関数ごとに生成され、2 つ目で `Connection refused`」と記録した。そこから [規則 §1.3](../README.ja.md) に「**1 実験 1 テスト関数**」を入れたが、**その制約が本当に一般的なのかは確かめていない**。

## 仮説

**E001 の観測は「host core の 2 回目の起動」に固有で、制約はもっと狭いかもしれない。** 根拠:

- `pytest-embedded` の `dut` fixture は **function scope 固定**で、scope を変えるオプションは見つからない。つまり「関数ごとに DUT を作り直す」こと自体は仕様。
- しかし作り直しが**失敗する**理由は別問題。host core は `socket://localhost` で毎回新しい port を開くので、前の実行の後片付けと次の起動が競合している可能性がある。

## 反証条件

1. 2 つ目のテスト関数でも DUT が正常に作られる(= E001 の観測が再現しない)
2. 2 つ目が失敗するが、原因が host core 固有ではない(実機でも同じ)
3. skip されるテスト関数でも DUT が作られ、そこで失敗する

## 方法

1. **host core で確認**: [E009](../e009_runs_archive/README.ja.md) のファイルはテスト関数を 2 つ持つ(`test_pass_case` / `test_fail_case`)。`-k` を付けずに実行し、2 つ目の DUT 生成が通るかを見る。
   - skip は fixture の setup **後**に起きるので、skip されるテストでも DUT は作られる(反証条件 3 の確認になる)。
2. **実機で確認**: 同じ構造の実験を実機 profile(`s3_peer_host`)で実行し、2 つ目の関数でも upload/接続が通るかを見る。
3. どちらも 2 回ずつ。

# 結果(2026-09-04)

計画は上のまま変更していない。以下は追記。

## 結果

| 環境 | 1 つ目の関数 | 2 つ目の関数 | 備考 |
|---|---|---|---|
| **host core**(常設 v0) | pass | **ERROR** `SerialException: Could not open port socket://localhost:<port>: Connection refused` | 2 つ目は `skip` するはずの関数だったが、**skip 以前に DUT 生成で落ちた** |
| **実機**(常設 v1、`s3_peer_host`) | **pass** | **pass** | 2 回とも。1 回目 17.21 s(build 込み)/ 2 回目 10.29 s |

| 反証条件 | 結果 |
|---|---|
| 1. 2 つ目でも DUT が正常に作られる | **実機では該当**(host core では非該当) |
| 2. 実機でも同じく失敗する | **起きず** — 制約は host core 固有 |
| 3. skip される関数でも DUT が作られる | **該当**(host core で確認) |

## 事実

1. **「1 実験 1 テスト関数」は一般的な制約ではない。** 実機では 2 つのテスト関数が問題なく動く(2 回とも 2 passed)。
2. **host core では 2 つ目の DUT 生成が失敗する。** `socket://localhost` の新しい port に接続できない(`Connection refused`)。**前の実行の後片付けと次の起動の競合**と見られる。
3. **skip されるテスト関数でも DUT は作られる。** `pytest.skip()` は fixture の setup **後**に走るので、DUT 生成の失敗は skip では避けられない。
4. **実機では関数ごとに再 upload される。** 単一関数の E004 が約 8.5 s に対し 2 関数で 10.3 s(build 済みの場合)。**関数を増やすと時間が増える**。
5. `pytest-embedded` の `dut` fixture は **function scope 固定**で、scope を変える公開オプションは見つからない。

## 候補

- **実機では複数関数を使ってよい**が、関数ごとに再 upload される分だけ遅くなる。**掃引のように 1 つの問いを繰り返すものは 1 関数の中でループする方が速い**(これまでの実験はすべてそうしている)。
- host core では 1 関数に限る。

## 未決

- host core の 2 回目が失敗する正確な原因(後片付けの競合か、port の再利用か)。**回避できているので追わない**。必要になったら上流に報告する材料として残す。

## 反映

- [規則 §1.3](../README.ja.md): 「1 実験 1 テスト関数」を**無条件の規則から、host core 限定 + 実機では速度上の推奨**へ緩める。
- [E001](../e001_smoke_host/README.ja.md) 事実 2 は host core の観測として正しい。**一般化しすぎていた**のを本実験が訂正した。
- 仕様の status は動かない。
