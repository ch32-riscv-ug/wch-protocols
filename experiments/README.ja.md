# 実測の規則(計画 → 実行 → レポート)

状態: **規則**(この repo の運用ルール。仕様ではない)。

この repo は「**実機で裏を取ってから `verified` にする**」を運用原則にしている([../README.md](../README.md))。その「裏の取り方」を、既存装置の観測([../captures/README.ja.md](../captures/README.ja.md))だけでなく、**自作 firmware を焼いて測る実測**まで広げるための規則。

道具は **[pytest-embedded-arduino-cli](https://github.com/tanakamasayuki/pytest-embedded-arduino-cli)** を使う — `arduino-cli` で build/upload、`pytest-embedded` で monitor。sketch 設定は `sketch.yaml` の profile、port は `.env` の `TEST_SERIAL_PORT_<PROFILE>`。`.env` は **`uv run --env-file .env pytest …`**(uv 側のオプション)で読ませる。線を見る実験では **sigrok(`sigrok-cli`)**を併用する。

## 0. 3 つの区別(これが最上位の分け方)

| 種別 | 何を得るか | 寿命 | 実行のされ方 |
|---|---|---|---|
| **capture** | 既存装置(WCH-Link / WCHISPTool / 純正ツール)の byte 列 | 一度取れば恒久 | 手動 + usbmon。[../captures/](../captures/) |
| **experiment** | 自作 firmware を焼いて得る数値・閾値・性能 | **一回性**。結果が成果物 | **明示指定でのみ**走る(§1.3) |
| **test** | 仕様どおり動き続けること | **恒久**。通り続けることが成果物 | まとめて走る |

置き場所: capture と experiment は**この repo**(`captures/` と `experiments/`)、test は実装側(`ch32rv-probe/tests/`)。

**experiment と test は道具もディレクトリ形も同じだが目的が逆**。experiment は「答えが出たら終わり」、test は「落ちたら困る」。混ぜると、答えの出た実験が CI を無駄に縛り、回帰テストが台帳を汚す。

**実験は台帳と同じ repo に置く**。理由は 3 つ: (a) 候補の多く(`linke-error-frame` / `isp-xor-key` / `iap-order` / `dap-mode`)は既存装置の観測で、実装側 repo と無関係。(b) 計画・コード・結果・台帳が repo を跨ぐと、参照に sha を打つ運用が要る。(c) この repo は既に `captures/` で証拠を持っており、実験はその延長。

**回帰テストだけは実装側**(`ch32rv-probe/tests/`)に置く。ライブラリと同じ寿命だから。CH32RVProbe firmware を使う実験は、**隣に clone してある実装 repo のパスを `.env` の `TEST_CH32RVPROBE_DIR` で受け取り**、`sketch.yaml` の `libraries: dir:` へ渡す(パスは環境固有なので §4.1 の原則どおり `.env` に入る)。

## 1. 置き場所

### 1.1 uv project と `.env`

**uv project は repo root ではなく `experiments/` に 1 つ。`.env` はその隣。**

```text
wch-protocols/
  protocols/  references/  captures/          ← 仕様・検討・既存装置の capture
  experiments/                               ← uv project はここ 1 つ
    README.ja.md                             ← 規則(本書)
    LEDGER.ja.md                             ← 台帳
    pyproject.toml  uv.lock  conftest.py
    .env  .env.example                       ← ベンチ固有値の唯一の入口(.env は commit しない)
    preflight.py                             ← 実行前のベンチ検査(§4.2)
    _runs/                                   ← 実行結果の退避先。追記のみ・消さない(§3.4)
    e001_harness_smoke/
      README.ja.md                           ← 計画(実行前) + レポート(実行後)。§3
      e001_harness_smoke.ino                 ← ディレクトリと同名(arduino-cli の要件)
      e001_harness_smoke.py                  ← test_ を付けない(§1.3)
      sketch.yaml
      build/<profile>/                     ← ビルド生成物だけ。実行のたびに破棄

ch32rv-probe/                                ← 実装側。回帰テストだけこちら
  library.properties  src/  examples/
  tests/                                     ← 別の uv project(回帰専用)

**「機材が共通なら `.env` は親に置きたい。すると uv も親になるのか」への答えは「ならない」。** `.env` は `uv run --env-file <path>` が**パスで受け取る**ので、uv project の位置と独立に置ける。ただし今回は**分ける必要がない**:

- **共通にしてよいもの** = 機材の物理構成(port、lane に繋いだ chip、LA のチャンネル、GND)。これは「机」の性質で、回帰と実験で変わらない。→ `.env` 1 つ。
- **共通にすると面倒なもの** = Python 依存(実験だけ解析・計測器ライブラリが要る)、pytest 設定、成果物の置き場。→ 分けたくなる**可能性**がある。

いまはこの 2 つ目がまだ発生していない(実験どうしは同じ依存)ので、**uv project は 1 つ**にする。将来グループごとに依存が割れても、`.env` は `experiments/.env` のまま `--env-file ../.env` で共有できる。**`.env` の位置は uv の分割方針を先に決めなくてよい**、が結論。

### 1.2 何をフォルダで分け、何を分けないか

| 軸 | フォルダにするか | 表現方法 |
|---|:--:|---|
| **調査の目的(問い)** | **する** | `experiments/<ID>_<question>/` 1 問い 1 ディレクトリ |
| **デバイス(probe MCU)** | **しない** | `sketch.yaml` の profile + `.env` の `TEST_SERIAL_PORT_<PROFILE>` |
| **target chip** | **しない** | `.env` の宣言 + テスト側の要求宣言(§4.1) |
| **調査対象(層)** | **しない**(当面) | 台帳の節。20 を超えたら 1 段グループ化 |

**デバイスをフォルダで分けない理由**は 3 つ。(a) profile と `TEST_SERIAL_PORT_<PROFILE>` が既にその軸を持っている。(b) このライブラリの主張は**移植性**なので、同じ実験が複数 board で走らないと意味がない — 分けると比較できなくなる。(c) 分けた瞬間に sketch が複製され、片方だけ直る。

**層でも分けない**(当面)。1 つの実験が線層と protocol 層を同時に答えることが普通にあり、ディレクトリは二重に置けない。

**台帳 ID をディレクトリ名の先頭に付ける**(`e001_swio_threshold/`)。仕様側の doc は「E001 で verified」の形で実験を**恒久的に引用**するので、ID が path に入っていれば台帳を開かずにコードへ辿り着ける。ID は起票時に確定し、**再利用も再採番もしない** — 中断した実験の番号は空けたまま、ディレクトリは記録として残す。

### 1.3 命名 — 実験は `test_` を付けない

| 種別 | ファイル名 | bare `pytest` で | 明示指定で |
|---|---|:--:|:--:|
| 回帰・unit | `test_<name>.py` | **走る** | 走る |
| **実験** | `<ID>_<name>.py`(例 `e001_swio_threshold.py`) | **走らない** | **走る** |

pytest の既定 `python_files = test_*.py` は**ディレクトリを辿るときの収集条件**で、**ファイルを明示指定したときは適用されない**(実測確認済み)。関数名は `test_*` のままでよい。

```sh
uv run --env-file .env pytest                                             # 何も走らない(実験しか無いので)
uv run --env-file .env pytest e001_harness_smoke/e001_harness_smoke.py    # ← 実験はこう明示する
```

**明示指定は「ファイルのパス」でなければならない。ディレクトリを渡すと 0 件になる**(E001 で実測)。ディレクトリ指定はその中を走査する動作で、走査には `python_files` の条件が効くため。

**1 実験 1 テスト関数にする。** DUT はテスト関数ごとに生成されるので、同じファイルに 2 関数書くと 2 つ目の DUT 起動が失敗することがある(E001 事実 2)。一実験一問い(§7-1)とも一致する。

**実験を明示指定でしか走らせないのは、起動の手間を惜しむより事故を避けるため。** 実機の実験は数十分の掃引・複数 board への書込・電源制御を含み、うっかり `pytest` を叩いて全部走ると時間も配線も壊す。一方、実験はもともと「計画を立てて 1 本ずつ回す」ものなので、明示指定はむしろ運用と一致する。回帰は逆に「まとめて走ってほしい」ので標準の `test_` を使う。**命名規約が §0 の区別をそのまま表す**。

保険として `.env` を読ませない限りベンチ変数が無く、実機を要するものは §4.1 の要求判定で skip される。**`--env-file` を付け忘れた実行は安全側に倒れる**。

## 2. 台帳

[LEDGER.ja.md](LEDGER.ja.md) が唯一の索引。**2 段構え**にする:

- **候補** — 問いと必要な機材だけを書く。**番号は付けない**。参照には slug(`swio-threshold` など)を使う
- **採番済み** — 機材が用意できることを確認した(§3.1)ものだけ。ID は **`E` + 3 桁の単一連番**(`E001`〜`E999`。種別は列で表し、番号は種別をまたいで一意)。ディレクトリは小文字(`e001_…`)

**3 桁にする理由**: 実験は**小さく割る**(§7-1)。1 つの問いに 1 実験を守ると、chip family(V003 / V00x / V103 / V20x / V30x / X03x / L103 / CH641 / CH643 / M0xx)× transport(UART / CDC / HID / TCP / WS)× 層で候補が積み上がり、2 桁は現実的に足りない。**番号は再採番しない約束なので、幅は最初に一度だけ決める必要がある** — 99 を超えてから `E100` に伸ばすと、ディレクトリの辞書順(`e100` < `e99`)が壊れて恒久的に残る。3 桁なら 1 文字払うだけでこれを避けられる。

ID は起票時に確定し、**再利用も再採番もしない**。だから「組めないベンチの実験」に番号を焼き付けないよう、確認を先に置く。

1 実験 1 節、結論は必ず次の 3 ラベルに分けて書く:

- **事実** — 観測から直接言えること。解釈を混ぜない
- **候補** — その実験の中だけで試した方式。採用ではない
- **未決** — 残った疑問。次の実験 ID か [../coverage.ja.md](../coverage.ja.md) の穴番号に結び付ける

**実験が通ったことを仕様の承認とはみなさない。** 仕様([../protocols/](../protocols/))の status を動かすのは §6 の証拠水準を満たしたときだけ。

## 3. 確認 → 採番 → 計画 → 実行 → レポート

### 3.1 採番の前に、機材が用意できるかを確認する

**問いを思いついた時点では採番しない。** まず [LEDGER.ja.md](LEDGER.ja.md) の**候補**(slug のみ、番号なし)に置き、**機材が用意できることを確認してから**採番して計画を書く。番号は再利用も再採番もしない約束なので、組めないベンチの実験に番号を焼き付けると欠番だけが残る。

確認するのは 3 つ: **その chip / board が手元にあるか**、**計測器が要るか・あるか**、**ベンチをどれだけの手間で組めるか**。3 つ目がベンチの種別になる。

| ベンチの種別 | 例 | 設営コスト | 運用 |
|---|---|---|---|
| **常設** | **v0 実機なし**(host Arduino core)/ v1 probe 1 枚 / v2 既設 peer 2 枚 | ゼロ〜挿すだけ | いつでも回せる。CI に載せられる。構成と約束は **§4.5** |
| **一時** | probe + target 1〜2 個をブレッドボードで配線し、数日〜数週間そのまま置く | 分〜時間 | その期間は何度でも回せる。配線を変えるまでは固定 |
| **使い捨て** | LA を特定ピンに繋ぐ / レベル変換を挟む / 珍しい chip を載せる / 電源制御を組む | **時間〜日** | ばらすと再現に同じコストがかかる。§3.1.1 |

#### 3.1.1 使い捨てベンチは「セッション」単位で計画する

設営に時間がかかるベンチでは、**単位は実験ではなくセッション**になる。

1. **組む前に棚卸しする。** そのベンチ構成で答えられる候補を候補一覧から**全部**拾い、まとめて採番して 1 セッションにする。「ついでに測れたはず」を後から取り返すのが一番高くつく。
2. **記録は今、解析は後。** セッション中は生データ(波形・ログ・銘板)を取れるだけ `_runs/` に取る(§3.4)。その場で解析して打ち切らない — **取り逃しは取り返せないが、解析はやり直せる**。
3. **ばらす前に「取れているか」だけ確認する。** 値が妥当かではなく、ファイルが空でないか・marker が付いているか・全掃引点が揃っているか(§4.3)。ここだけは撤収前にやる。
4. **配線を記録に残す。** ピン対応表と写真を `_runs/` に入れる。次に同じベンチを組むときの設営コストがこれで下がる。
5. 常設・一時で代替できないかを先に考える。LA が要ると思った問いが loopback phy(§4.4)で答えられることがある。

#### 3.1.2 最初の実験はハーネスのスモーク

**何よりも先に、ハーネス自体が通ることを確かめる。** build / upload / monitor / `.env` の port 解決 / 銘板 / `_runs/` への退避 / device lock — これが動かないうちに測った数値は、測定対象ではなく環境を測っている。最初の 1 本は「答えが yes/no のスモーク」にして、以後の全実験がその上に乗る形にする。

### 3.2 計画は実行より先に commit する

`experiments/<ID>_<question>/README.ja.md` に、**コードを書く前に**次を書いて commit する:

```markdown
# E012 SWIO パルス幅閾値
状態: 計画    <!-- 計画 → 実行中 → 完了 / 中断 -->

## 問い       一文。答えが数値か yes/no になる形にする
## 仮説       予想と根拠(既存資料へのリンク)
## 反証条件   何が観測されたらこの仮説は間違いか
## 方法       手順。掃引する変数と範囲、固定する変数
## 対象外     この実験で答えないこと。別の問いに割ったものは slug か ID で指す
## 必要な環境 probe profile / target chip / 計測器 / 配線 / LA チャンネル
## ベンチ種別 常設 / 一時 / 使い捨て。使い捨てなら同じセッションで一緒に取る問いを列挙
## 記録する数値 列名と単位。繰り返し回数
## 完了条件   これが得られたら完了。得られなくても完了とする条件
## 影響       どの doc の status がどう動きうるか
```

### 3.3 レポートは同じファイルに追記する。計画は書き換えない

```markdown
## 結果       表。生ログ・波形の位置(§5)
## 事実 / 候補 / 未決
## 反映       更新した doc と status、台帳の節
```

**計画を結果に合わせて書き換えない。** 問いや方法が変わったら、その実験は「中断」にして**新しい ID を起こす**。git 履歴に「先に何を問うたか」が残ることが、この規則の目的そのもの。

### 3.4 結果は退避する。再実行で消えてはいけない

実験の結果は**書き換えられない場所に、実行のたびに新しく作る**。

| 場所 | 中身 | 寿命 |
|---|---|---|
| `<実験>/build/<profile>/` | ビルド生成物(plugin が `--build-path` に渡す位置) | **実行のたびに破棄してよい** |
| `experiments/_runs/<ID>_<UTC>_<profile>/` | 生ログ・波形(`.sr`)・数値・銘板 | **追記のみ。上書きも削除もしない** |
| `../captures/fixtures/` + 台帳 | レビューを通した証拠だけ | 恒久(commit する) |

**結果を `build/` に書かない。最初から `_runs/<ID>_<UTC>_<profile>/` に書く。** 実験ファイルは `test_` を付けない(§1.3)ので誤爆しにくいが、それでも意図しない再実行は起きる。そのとき失うのが「時間」だけで済み、「前回の測定結果」が消えないようにするための分離。run ディレクトリ名に UTC を含めるので、同じ実験を何度回しても過去の run は残る。

レポート(§3.3)には**どの run ディレクトリの数値か**を書く。人がレビューしてから、証拠として残す分だけ [../captures/fixtures/](../captures/) の流儀で注釈を付けて commit し、台帳に節を書く。実行と採用を分けることで「走ったから正しい」を避ける。

`_runs/` は commit しない(生ログは大きい)。消すのは人の判断で明示的に行う。

### 3.5 完了の条件

台帳に節ができ、`状態: 完了` になり、**未決が次の行き先(実験 ID か coverage の穴番号)を持っている**こと。「答えが出なかった」も完了。

## 4. ベンチ

### 4.1 `.env` がベンチ固有値の唯一の入口

port だけでなく **probe の GPIO 番号や LA のチャンネルまで `.env` に置き、コンパイル時 define として sketch に注入する**(`--build-property` 経由)。**ベンチに合わせて書き換えるのは `.env` だけで、sketch は触らない**。

```sh
# probe board の port(profile ごと。PROFILE は sketch.yaml の profile 名を大文字化)
TEST_SERIAL_PORT_ESP32S3=/dev/ttyACM0
TEST_SERIAL_PORT_PICO=/dev/ttyACM1

# probe の pin(sketch へ define で注入。lane の構成そのものは sketch が決める)
TEST_LANE0_SWIO=2
TEST_LANE1_SWCLK=4
TEST_LANE1_SWDIO=5
TEST_MARKER_TX=3

# 各 lane に何が繋がっているか(実験の要求判定に使う)
TEST_TARGET_ESP32S3_LANE0=ch32v003
TEST_TARGET_ESP32S3_LANE1=ch32v307

# ロジックアナライザ
SIGROK_DRIVER=fx2lafw
SIGROK_SAMPLERATE=24000000
SIGROK_CH_SWIO=D1
SIGROK_CH_MARKER=D0

# 基準装置
TEST_LINKE_PORT=/dev/ttyACM2
```

**テストは必要な環境を宣言し、無ければ理由付きで skip する。** 誰のベンチでも「持っている分だけ」走る。**レポートは「未測定」と「合格」を必ず区別する** — skip を成功として数えず、台帳の表では未測定を `—` と書いて空欄にしない。

### 4.2 preflight

実機を触る前に、`.env` の欠落・pin の重複・LA のチャンネル重複・`sigrok-cli --scan` の応答・port の存在を検査する `preflight.py` を通す。配線を間違えたまま 30 分の掃引を回さないための安全ゲート。

### 4.3 marker 線

**LA だけが見る専用線を 1 本引く。** ホストには繋がない。probe はここへ「いまの試行番号・掃引値・フェーズ」を出し、LA が SWIO/RVSWD と**同時に**取得する。これが無いと、波形のどの区間がどの設定だったのかを後から特定できない。UART TX を marker にして decode するのが扱いやすい(数値を載せられる)。GPIO のパルス数でも代用できる。

### 4.4 2 台目のボード(dummy peer)をどこまで使うか

プラグインは `--peer-profile` / `--peer-port` で 2 台目を扱え、device lock も peer ごとに効く。ただし**使う前に、線を出さずに済ませられないかを先に考える**。

| 用途 | 判断 | 理由 |
|---|---|---|
| **probe 内の loopback phy**(実際の線を出さず、DMI トランザクションに定型応答を返す疑似 phy) | **まずこれをやる** | ボードが 1 台で済み、**DMI status の fail / busy、無応答、CRC 誤りを任意に注入できる**。transport・多重化・コマンド層([dmi-bridge](../protocols/dmi-bridge.ja.md) §2–§4、`batch`、`tag` 再送、event)はここで全部測れる。実チップでは誤りを狙って起こせない |
| 実 target(V003 / V307 …) | **線層と性能はこれで** | 線の実波形・タイミング・実書込時間は実チップでしか測れない |
| 線を喋る dummy target(2 台目が SWIO/RVSWD の target 側を演じる) | **やらない**(当面) | target 側は読出し位相で厳しいタイミングを守る必要があり、実装コストが線層の実験そのものと同程度。得られるものは実チップ + LA で足りる |
| ボードを LA 代わりに使う | **やらない** | サンプルレートと同時取得数で専用機に及ばない。LA は安価 |
| target UART へ既知の系列を流す peer | **必要になったら**(uart bridge の実験) | 安く、実装も小さい |

**線引きは「線を含むか」で引く。** 線を含まない層は loopback phy で 1 台のまま徹底的に測り、線を含む層だけ実チップ + LA を用意する。この分業なら、回帰([dmi-bridge](../protocols/dmi-bridge.ja.md) §8.1 の Core / Bulk 相当)を**ボード 1 台で CI に載せられる**。

### 4.5 常設ベンチ — 置くか、何を置くか

**置く。** 回帰の基準が無いと、実験の失敗が「実験のせい」か「環境のせい」か切り分けられない。常設が緑であることが他の全実験の前提になる(§3.1.2)。

**ただし最初の常設は実機ではない。** 3 段の梯子にして、**下の段で答えられる問いを上の段に持ち上げない**。

| 段 | 構成 | 設営 | ここで答えられること | ここでは答えられないこと |
|---|---|---|---|---|
| **v0** | **実機なし。host Arduino core**(`lang-ship:host:host` / `socket://localhost`) | ゼロ | pytest ハーネス、frame/CRC、`batch` の符号化、`tag` 再送、`caps`/`info` の TLV、loopback phy の**論理**、**線の bit 列** | **時間**(仮想時計)、USB、実際の電気 |
| **v1** | 実機 1 枚(ESP32-S3) | 挿すだけ | build/upload/monitor、UART・USB CDC・IP transport、**実時間**、device lock、DTR reset | 線の波形、target の応答 |
| **v2** | 実機 2 枚(既設の peer 対。**GPIO18/19 が直結済み**) | **ゼロ**(既にある) | 2 台同時 upload と lock、**2 線の相互観測** | 実 CH32 の挙動 |
| (以降) | 実 CH32 target | 一時 / 使い捨て | 線の波形、実書込性能 | — |

#### v0 — 実機なしでどこまで行けるか(想像より遠い)

host Arduino core は sketch を PC 上で走らせ、`socket://localhost` で `dut.expect` に繋がる。**線層は「符号(bit 列)」と「タイミング(パルス幅)」に分けられ、符号の方は実機なしで検証できる**:

- SWIO の 1 トランザクション(start + addr7 + start + data32)、RVSWD の 7+32+2+1 ×2、parity の計算 — **GPIO の遷移列として観測できる**([link-to-target](../protocols/link-to-target.ja.md) §3 の bit フレームがそのまま検算できる)
- frame の magic/len/CRC、`batch` の op 符号化と結果の並び、`tag` 再送のキャッシュ、`caps` TLV の往復 — 全部ただの計算

**LA が要るのはタイミングだけ**になる。使い捨てベンチ(§3.1.1)で取るべき問いがその分減るので、**v0 を先に作り切ってから実機に降りる**のが最も安い。

**v0 で測ってはいけないもの**: 時計は仮想なので、**性能・latency・パルス幅の数値は一切ここから取らない**(§6、§7-2)。

#### v1 — 実機 1 枚

`.env` の `TEST_STANDING_PROFILE` で 1 枚を指名し、preflight(§4.2)が最初に確認する。board は **ESP32-S3** を推す — **UART / native USB CDC / IP の 3 transport を 1 枚で試せる唯一の選択肢**で、IP は ESP32 系にしか無い。内蔵 USB-Serial-JTAG(`303A:1001`)なら driver レスで USB ID の固定費もゼロ。Pico は PIO の決定論が魅力だが IP が無く覆う範囲が狭いので、**一時ベンチ側の「移植性の確認」担当**に回す(同じ実験が 2 枚目で通るか、が Pico の役目)。

#### v2 — peer(既設の 2 枚)

既に 2 枚が常設され、**GPIO18/19 が相互に直結されている**(元は USB D+/D− の試験用)。**RVSWD は 2 線(SWCLK + SWDIO)なので、配線を一切変えずに 2 線ペアの形が既に存在する**。

やるかどうかは別として、**使えるかどうかの確認だけは先にしておく**(台帳 E003)。確認するのは「2 台へ同時に upload できるか」「device lock が 2 枚それぞれに効くか」「片方の GPIO 遷移をもう片方が観測できるか」まで。ここが通れば、後で「線を喋る dummy target」を作る選択肢が残る(§4.4 では実装コストを理由に見送ったが、**配線コストがゼロなら判断が変わりうる**)。

#### 常設の約束(守れないならそれは常設ではない)

1. **配線を変えない。** 実験で使いたくなったら別の board を使う。抜いた瞬間に常設でなくなる。
2. **専有する。** 常設の board を他の実験に流用しない。
3. **短時間で終わる。** 常設で走るものは数分以内。長い掃引は実験側に置く。
4. **常設が赤いときは他の実験を始めない。** 環境が壊れている合図なので、先にそれを直す。
5. **下の段で答えられる問いを上の段でやらない。** v0 で足りるものを実機で測ると、壊れやすい場所が増えるだけで得るものが無い。

#### port 名は別名でよい

シリアルポート番号は挿し直しで変わるので、`.env` には**安定した別名**(`/run/board-identify/by-id/<board>` のような固定パス)を書いてよい。プラグインは device lock のキーを作るときに **symlink を解決してから**ハッシュするので、別名でも実体の board に対して正しく排他が効く。`.env.example`(commit する側)は環境非依存にするため `/dev/ttyACM0` 等の一般的な表記で書く。

## 5. 記録

**銘板** — sketch は `setup()` の最初に 1 行出し、テストはそれを前提条件として `expect` する:

```text
# EXP E012 v1 fw=e2f1a9c core=rp2040:3.9.4 probe=pico target0=ch32v003 t=2026-09-04T11:20:00+09:00
```

`pytest-embedded` は `<tmpdir>/pytest-embedded/<UTC>/<test 名>/dut.log` に生ログを残す。銘板があれば、**その 1 ファイルだけで実験 ID・firmware・core 版・board・target・日時が復元できる**。台帳にはこのログと `.sr`(波形)の位置を書く。

**`<実験>/build/` は `conftest.py` が実行のたびに破棄する** — そこに入るのはビルド生成物だけ。前回の生成物が残っていると、ビルドし損ねた回を成功と読み違える。**測定結果は §3.4 のとおり `_runs/` に退避する**ので、この破棄で失われるものは無い。

**replay を用意する。** commit した波形・capture を decode し直して、記録済みの結果と一致するかを確認する `unit/` テストを置く。デコーダや parser を触ったとき、実機なしで壊れていないかが分かる。

## 6. 証拠の水準 — 何をもって `verified` と呼ぶか

status 語彙([../README.md](../README.md))と対応させる。**自己申告は `verified` にならない。**

| 主張の種類 | 必要な証拠 | 到達できる status |
|---|---|---|
| 線上の波形・パルス幅・クロック | **ロジックアナライザ / オシロ**での独立観測 | `verified` |
| USB の byte 列 | usbmon / Wireshark の capture | `verified` |
| protocol の往復・値・順序 | 実機ログ(銘板つき)+ **独立実装 2 つの一致** | `verified` |
| 同上、実装 1 つのみ | 実機ログ | `attested` |
| 性能・時間 | MCU 内で計測した数値(§7-2) | `attested`(条件を明記すれば実用上十分) |
| firmware の自己申告のみ | — | **`attested` 止まり** |
| **線の bit 列・符号化**(パルス幅を含まない) | host Arduino core での GPIO 遷移列 | `attested`(符号のみ。波形は §6 の 1 行目が要る) |
| **時間・性能を host Arduino core で測った値** | — | **証拠にしない**(仮想時計) |

線層(SWIO のパルス幅など)を firmware の自己申告で `verified` にしない。probe が「送ったつもり」の値と線に出た波形は別物で、[link-to-target.ja.md](../protocols/link-to-target.ja.md) の穴はまさにそこにある。

## 7. 測り方の規則

1. **一実験一問い。小さく割る。** 2 つ答えたくなったら 2 ディレクトリに割る。計画に **`対象外`** を必ず書き、そこへ落としたものは候補へ戻すか別 ID を立てる。大きい実験は落ちたときに「どこが原因か」を答えられない。
2. **時間は MCU 内で測る。** `micros()` で挟んで数値を print する。**host Arduino core(§4.5 v0)の時計は仮想なので、そこから性能値を取らない。**host 側で serial の往復時間を測ると、測っているのは USB-CDC の latency であって protocol ではない。transport の latency を測りたいときは、それを**別の実験**として明示的に立てる。
3. **3 回以上繰り返し、min / median / max を出す。** 1 回の値を事実にしない。timing は特に。
4. **掃引は端から端まで。** 閾値を探すときは「動く値」を 1 つ見つけて満足せず、**動かなくなる境界の両側**を記録する(SWIO のパルス幅なら、短すぎて壊れる点と長すぎて壊れる点の両方)。
5. **pytest の緑/赤は「収集の構造が壊れていないか」の判定であって、測定値の正しさの判定ではない。** 数値が妥当かどうかはレポート(§3.2)で人が判断する。テストを緑にするために閾値を緩めない。
6. **異常は failure にせず観測として残す。** target の timeout、想定外の DMI status、ログ中の疑わしい行は、テストを落とさずサマリーに集計して台帳へ回す。落とすと、原因を調べる前に「直して緑にする」圧力がかかる。
7. **失敗・不発も commit する。** 「測ったが分からなかった」は未決として台帳に残す。残さないと同じ実験が繰り返される。
8. **比較には基準装置を入れる。** 可能なら同じ操作を WCH-LinkE + `ch32rv` でも実行し、同じ列に並べる。自作 probe の数値だけでは速いのか遅いのか判断できない。
9. **device lock を切らない。** 複数 board を並べるベンチでは `--device-lock`(既定 `auto`)に任せ、port を直書きしない。
10. **LA と MCU の GND を必ず共通にする。** 波形の測定でここを外すと、測っているのはノイズになる。
