# E004 スモーク: 実機、host からの trigger で応答させる

状態: **完了**(2026-09-04)    <!-- 計画 → 実行中 → 完了 / 中断 -->

規則: [../README.ja.md](../README.ja.md) / 台帳: [../LEDGER.ja.md](../LEDGER.ja.md) / 前段: [E002](../e002_smoke_board/README.ja.md)(反証された)

## 問い

**host が trigger を送ってから応答させれば、起動時出力の取りこぼし(E002 事実 2)を回避して銘板と実時間を取れるか。**

## 仮説

**取れる。** [E002 候補 (c)](../e002_smoke_board/README.ja.md) の方式。監視の接続が reset より 1 秒以上遅れても、**応答は host が要求した時点で生成される**ので接続タイミングに依存しない。

これは [dmi-bridge §4.1](../../protocols/dmi-bridge.ja.md) の `hello`(host が撃ち、probe が答える。成立して初めて他のコマンドを送ってよい)と、[ecosystem-any-hardware §4.5](../../references/ecosystem-any-hardware.ja.md)(DTR 副作用は host が `hello` 待ちで吸収する)を、そのまま最小形にしたもの。

## 反証条件

1. trigger を送っても応答が返らない(受信側が動いていない、取りこぼす)
2. 応答は返るが**銘板が 1 行として読めない**
3. `micros()` の差分が**実時間として妥当でない**(900〜1500 us に入らない)
4. 1 回目の trigger には応答しないが 2 回目以降は返る(= **再送が必要**。回避はできるが「1 発で取れる」は否定される)

## 方法

1. sketch: `setup()` では何も出さない。`loop()` で 1 byte 読み、`?` を受けたら**銘板 + 既知 3 行 + `CLOCK delta=` + `SMOKE done`** を返す。
2. test: `dut.write("?")` → 応答を expect。**応答が無ければ最大 3 回まで再送**し、何回目で返ったかを記録する(反証条件 4)。
3. `CLOCK delta=` が 900〜1500 us に入ることを assert。
4. 3 回繰り返す。

## 事実

1. **host が撃って probe が答える形にすれば、監視の接続タイミングに依存しない。** E002 で確定的に失われた起動時出力が、この方式では 3/3 で取れた。**再送も不要**(1 発)。
2. **実クロックが取れる。** `delayMicroseconds(1000)` に対して `micros()` の差分は **1003 us**、3 回とも同値。仮想時計(常設 v0)と明確に区別できる。→ **E002 で未測定だった項目に答えが出た。常設 v1 が成立**。
3. `setup()` で何も出さない設計にすると、`dut.log` に**応答だけ**が残る。取りこぼしと「そもそも出していない」の区別が要らなくなる分、ログが読みやすい。

## 候補

- **実機実験の共通の型 = 「host が撃つ → probe が答える」**(採用)。E002 候補 (a) 周期再送 / (b) host からの reset は**試さずに済んだ**。必要になるまで未検証のまま残す。
- **代替の型: board が ready を定期送出 → host が開始を指示。** 初期化に時間がかかる、あるいは受信を始められるまでに間がある board ではこちらが要る。**reset 後にシリアルが流れ始める時刻は board 依存**なので、いずれにせよ**固定待ちでは合わせない**([規則 §7-10](../README.ja.md))。今回の board では (A) で足りたため未検証。

## 未決

- trigger を frame 化したとき(magic + len + CRC、[dmi-bridge §2.3](../../protocols/dmi-bridge.ja.md))も同じく 1 発で通るか → protocol 実装時に確認する。
- 起動直後(reset から 1 秒未満)に trigger を撃った場合の挙動は見ていない → 候補 `uart-dtr-reset`。
